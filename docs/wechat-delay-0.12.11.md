# 小程序额外等待调查（0.12.11）

用户确认使用 Shizuku；执行记录显示 clickCenter / Shizuku / InputManager，录像底部文字由用户自定义的跳过提示产生。无需再将本次现象归因于未授权或未接入增强通道。

按录像时间轴约 0.1 秒采样：第一次约 4.4 秒出现广告，5.5 秒开始关闭；最后一次约 24.6 秒出现广告，25.5 秒已出现执行提示，27.5 秒才开始关闭。正常样本约 1.1 秒，与规则原有 800ms 延迟加查询 / 过渡时间相符；慢样本在受理提示后还有约 2 秒停留。提示与接口成功不能作为广告已关闭的判据，也不能仅据录像判定首次触摸失效的具体驱动原因。

## 已确认的执行差异与修正

GKD 固定提交的 A11yRuleEngine 在同步动作受理后继续遍历本轮其他规则，并在规则查询前刷新节点；通过前台 / 状态 / 规则检查阻止过期操作。原 NoAdMi 在首个动作受理后直接 break，其他规则需要后续检查才能执行。

0.12.11 保留每条规则本轮至多访问一次的顺序遍历。同步成功后，下一条符合条件的规则查询前重新读取并 refresh 当前窗口，关闭旧节点树；再次检查包名、事件代次、总开关和订阅修订，再查询及执行。异步无障碍手势仍等待回调。没有在同一条已成功的规则后强行补发坐标点击，不复用点击前的目标，不修改第三方订阅的 800ms 延迟、冷却、次数或前置条件。

## 输入参数对照

GKD Android 12+ 的 InputShellCommand 使用虚拟设备编号 0；NoAdMi 原采用可用触屏设备编号。曾在 code87 对照编号 0，当前 MIX Fold 3 上接口受理但测试页未收到触摸事件，因此此项未作为最终包的默认修改。code88 保留 0.12.10 已验证的 InputManager 输入参数，并新增夹具实际接收触摸的验证。不能把本机失败推广到其他手机，也不能据此认定故障手机驱动的根因。

## 验收边界

最终 code88 的隔离夹具：第一条规则点击后删除原按钮并新建第二条规则的目标；五轮均重新读到新目标、每条各执行一次，第二步间隔约 15～17ms。Shizuku 坐标点击五轮均关闭页面且实际收到触摸。Root 延迟节点方式及原设置保留见 SMART_SKIP_VERIFICATION.md。

故障手机尚未连接；微信小程序实际延迟与稳定性仍需该手机复测。录像、截图及原订阅不打入源码包。本轮未发布 GitHub。
